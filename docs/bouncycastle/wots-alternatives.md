# Bouncy Castle WOTS alternatives

The object-only address hoist reduced per-operation allocated bytes across all six fast SLH-DSA configurations: 7.21–10.19% in key generation and 5.52–8.23% in signing. It remains the narrowest allocation candidate for further review. This study establishes no broad latency improvement; larger changes retained substantial losses, and unchanged verification controls shifted materially.

Six isolated implementations start from Bouncy Castle `c314b9cdffa3958a0eff5344f8fdcdb0181ed830`: stock, object-only address reuse, a same-allocation field/type rewrite, the previous two-address comparator, the old chain buffer, and its peeled-loop alternative. No persistent cache crosses keys or calls. [Source changes and reproduction](../../libs/bouncycastle/experiments/wots-alternatives/README.md) describe exact overwrite, domain-separation, ownership and chain-range requirements.

Each variant passed 24 dirty-address transcript cases at n=16/24/32, 2,514 real SHA2/SHAKE chain cases, and 234 whole-operation checks. Whole-operation coverage uses all twelve fixture keys for each of six fast sets and one distinct key for each of six slow sets, through key generation, signing and verification. Checks cover exact outputs, caller ownership, entropy consumption, retained outputs and tampered signatures. The transcript engine is a test double. Root additionally ran the pinned native full verification methods, component lengths and uninitialized-signer checks against all six sealed variants; that evidence is linked in the coordinated alternative-comparison report.

The initial screen ran 288 fresh JVMs for six comparisons, SHA2/SHAKE-128f, three operations, separate latency/allocation modes and two balanced AB/BA pairs. Each JVM used twenty warmup calls on two keys, then measured ten other distinct keys once each. Operation initialization is inside the interval; key decoding is outside. Twenty warmups and two pairs do not establish steady state. The [complete screen table](../../results/bouncycastle/wots-alternatives/table.md) preserves every comparison, loss and unchanged verification control. [Raw summary](../../results/bouncycastle/wots-alternatives/summary.json) percentages divide the mean of two candidate process means by the corresponding reference mean, retaining each pair and absolute means.

The field rewrite improved SHA2-128f signing in both pairs (wall −4.29%/−3.36%, CPU −3.81%/−3.29%) but consistently slowed key generation (wall +6.08%/+6.15%, CPU +5.60%/+6.07%). It advanced through the frozen rule's improvement branch despite that loss. The peeled buffer failed the direct-stock rule: SHA2-128f key-generation wall time rose +4.23%/+5.30% and CPU rose +4.43%/+5.35%, with no targeted cell meeting the repeatable-improvement threshold. Its favorable comparisons against the old buffer do not establish a stock improvement.

The prespecified [selection](../../results/bouncycastle/wots-alternatives/selection.json) advanced the object hoist, field rewrite, two-address comparator and old buffer. Their selected followup ran 384 fresh processes across every SHA2/SHAKE-192f/256f configuration with the same counters, warmups, measured-key count and paired order. This is conditional followup, not a significance test; no mechanisms were combined. All 48 combinations appear in the [higher-size table](../../results/bouncycastle/wots-alternatives/confirmation/table.md), with both pairs in its [summary](../../results/bouncycastle/wots-alternatives/confirmation/summary.json).

The old buffer reduced allocated bytes by about 61–77% across the six fast sets, but SHA2-256f key generation rose +9.58% wall/+6.90% CPU and verification rose +15.85%/+15.73%. Both verification pairs lost (wall +14.04%/+17.73%, CPU +13.78%/+17.76%). SHAKE-192f verification also lost in both pairs, aggregating +3.06% wall/+2.92% CPU. Allocation savings do not establish an acceptable latency tradeoff.

SHA2-256f key generation rose +6.35% wall/+5.94% CPU for the field rewrite and +6.16%/+5.62% for the two-address comparator, with both pairs worse. The object hoist also had an aggregate loss there (+4.32%/+3.48%), although its pairs differed. SHA2-192f two-address signing's apparent −8.14% wall improvement was only −1.64% CPU and did not repeat across pairs (wall −15.12%/+0.16%). The more involved address changes therefore establish no general advantage over the object-only hoist.

Unchanged verification controls materially limit speed attribution. SHA2-192f object-hoist verification shifted +12.19% wall/+11.83% CPU and field-rewrite verification shifted +6.27%/+6.32%; SHA2-256f field-rewrite verification shifted +6.70%/+6.66%. These paths have no intended algorithm change. Process/JVM/code-layout or host effects can be material under this protocol, but these observations do not identify a single cause. Repeated changes or matching wall/CPU direction alone do not prove a source-level speed benefit.

The [shared-source local audit](../../results/bouncycastle/wots-alternatives/independent-audit.json) and [saved-data portable audit](../../results/bouncycastle/wots-alternatives/portable-audit.json) passed all 288 initial processes, 2,880 rows and 72 summary cells. The [followup audit](../../results/bouncycastle/wots-alternatives/confirmation/independent-audit.json) passed all 384 processes, 3,840 observations and 96 cells; root independently reran it. Portable checks explicitly report skipped or unavailable local binaries. [Correctness gates](../../results/bouncycastle/wots-alternatives/gates.json) and the [manifest](../../results/bouncycastle/wots-alternatives/manifest.json) retain source/runtime/corpus identities. Seals establish what ran, not oracle independence.

The coordinator excluded other agents' benchmarks/builds during collection, but the host was not isolated; earlier snapshots showed substantial `fseventsd` CPU use without establishing its activity throughout either window. Pair reversal does not eliminate JIT, GC, scheduling or thermal effects. The followup lasted 593.0 seconds; its longest complete JVM was 5.62 seconds and largest interprocess gap 4.22 ms. The [post-hoc duration diagnostic](../../results/bouncycastle/wots-alternatives/confirmation/durations.json) flagged no process above ten seconds or three times its comparable-work median, nor a gap above one second. These descriptive thresholds never excluded samples and cannot rule out shorter disturbances. Every process and observation was retained without selective reruns. Allocated bytes measure traffic; peak live heap, RSS, stack use, retained heap and GC pauses were unmeasured.

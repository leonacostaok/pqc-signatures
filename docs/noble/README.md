# noble — `@noble/post-quantum` (pure JavaScript)

| | |
|---|---|
| Library | [`@noble/post-quantum`](https://github.com/paulmillr/noble-post-quantum) **0.7.1** (deps: `@noble/hashes` 2.4.0, `@noble/curves` 2.4.0, `@noble/ciphers` 2.4.0) |
| Language / runtime | JavaScript (ESM). Baseline runtime **Node 22.22.0** (V8). One variant per process uses **Bun 1.4.2** (JavaScriptCore). |
| Harness | `libs/noble/run.sh` — `build`, `vectors`, `crossverify`, `bench` per `common/CONTRACT.md` |
| Parameter sets | ML-DSA-44/65/87, all 12 SLH-DSA sets (SHA2/SHAKE × 128/192/256 × s/f), Falcon-512/1024 (cross-verify + self-consistency only) |
| Docs | this file, [keygen.md](keygen.md), [sign.md](sign.md), [verify.md](verify.md) |

noble is an audited, dependency-free, *pure JS* implementation: no WebAssembly, no native
addons. Everything — SHAKE, SHA-2, the NTT, the hash trees — runs as JavaScript on the engine's
JIT. That makes it the slowest library in this comparison by construction, and it also makes it the
most malleable: every variant below is a change at the JavaScript level (which hash code runs, how
polynomials are represented, what is cached, which JIT runs it, how many threads).

## Seeded key generation and deterministic signing

Everything needed by the contract is in noble's documented API, so no RNG hooks are required:

| | ML-DSA | SLH-DSA | Falcon |
|---|---|---|---|
| keygen | `alg.keygen(seed)` with the 32-byte `xi` → FIPS 204 `ML-DSA.KeyGen_internal` | `alg.keygen(seed)` with the 3n-byte `SK.seed ‖ SK.prf ‖ PK.seed` → FIPS 205 `slh_keygen_internal` | `alg.keygen(seed)` with noble's own 48-byte seed (SHAKE256-driven NTRU solver) |
| sign | `alg.sign(msg, sk, { extraEntropy: false })` → `rnd = 0^32` (FIPS 204 deterministic mode), pure ML-DSA, empty context | `{ extraEntropy: false }` → `opt_rand = PK.seed` (FIPS 205 deterministic mode), pure SLH-DSA, empty context | `{ extraEntropy: false }` → the sampler/nonce DRBG is seeded with 48 zero bytes, so signatures are deterministic for (sk, msg) but noble-specific |
| verify | `alg.verify(sig, msg, pk)` | same | same |

`common/reference.json` was itself generated with these calls on the unmodified package
(`common/gen-reference.mjs`), so the 15 ML-DSA/SLH-DSA sets are byte-matchable. Falcon has no
cross-library byte reference (seed formats are not interoperable); for Falcon every variant is
compared against the *unmodified baseline's* output for the same seed/message computed at run time
(`src/refcheck.mjs`), plus self-verify and tamper rejection. The `reference` field of each result
line says which of the two was used (`common/reference.json` or `baseline`).

`match` is computed on every run, never hard-coded: keygen compares SHA-256(pk) *and* SHA-256(sk);
sign compares SHA-256(sig) of the first output and byte-compares every later output to it;
verify requires `true` on the reference triple and `false` on a one-bit-flipped signature.

## Layout and build

```
libs/noble/
  run.sh                 entry point (build | vectors | crossverify | bench)
  package.json           {"type":"module"} only — no extra dependencies
  patches/*.patch        diffs against node_modules/@noble/post-quantum/{ml-dsa,slh-dsa,falcon}.js
  build/vendor/          (generated by `build`) fresh copies of noble's sources + the patches
  src/
    algs.mjs             backend registry: pkg (baseline) | vendor (patched noble) | fast (rewrites)
    hashlayer.mjs        hash-layer switch for vendor/fast: @noble/hashes or node:crypto (NOBLE_PQ_HASH)
    native-hash.mjs      node:crypto drop-in shim for shake128/shake256/sha256/sha512/hmac + XOF readers
    fast-keccak.mjs      generated, fully unrolled Keccak-f[1600] (2.4x noble's keccakP)
    fast-shake.mjs       SHAKE128/256 + XOF readers on fast-keccak
    fast-ml-dsa.mjs      ML-DSA hot-path rewrite (lazy branch-free NTT, fused MAC, no allocations)
    fast-slh-dsa.mjs     SLH-DSA hot-path rewrite (direct compression-function calls, no ADRS objects)
    variants.mjs         the 18 variants
    bench.mjs            spawns one process per (variant, param); bench-one.mjs measures; worker.mjs = threads
    timing.mjs           warm-up / budget / percentiles / CPU accounting
    vectors.mjs, crossverify.mjs, refcheck.mjs
```

`run.sh build` is idempotent and works offline after the first `npm install`: it copies
`ml-dsa.js`, `slh-dsa.js`, `falcon.js`, `_crystals.js`, `utils.js` from `node_modules` into
`build/vendor/` and applies `patches/*.patch` with `patch`, then smoke-tests all three backends
against one reference vector.

### What the patches change (the "vendor" backend)

The vendored copies are noble's shipped JS with three kinds of additive edits (158/129/73 changed
lines for ml-dsa/slh-dsa/falcon; see `patches/`):

1. **Pluggable hash layer.** `import { shake256 } from '@noble/hashes/sha3.js'` (and the SHA-2,
   HMAC and `XOF128`/`XOF256` imports) become imports from `src/hashlayer.mjs`, which re-exports
   either `@noble/hashes` (default, bit-identical to the baseline) or the `node:crypto` shim
   (`NOBLE_PQ_HASH=native`).
2. **Per-key precomputation APIs**, used by `sign.v3` / `verify.v3`: `expandSk(sk)` +
   `signPrecomputed(msg, exp, opts)` and `expandPk(pk)` + `verifyPrecomputed(sig, msg, exp)`.
   The original `sign`/`verify` are re-expressed as "expand, then run the per-message part"
   so the baseline path is unchanged apart from function boundaries (the per-message code is
   the original code; the cached material is simply not zeroized between calls).
3. The factories `getDilithium` / `gen` are exported (unused by the harness, handy for tests).

The **fast** backend (`src/fast-*.mjs`) is a separate rewrite of the hot paths that reuses noble's
packing/coder helpers and parameter tables; it supports only what the benchmark needs (pure mode,
empty context, deterministic signing) and is documented in the per-process files.

## Variant matrix

Each process has a baseline (`v0`) and five alternatives. Mechanisms are shared where they apply
to several processes, but each process' list was chosen for that process:

| | keygen | sign | verify |
|---|---|---|---|
| v0 | baseline | baseline | baseline |
| v1 | native-hash (node:crypto SHAKE/SHA-2) | native-hash | native-hash |
| v2 | fastjs (rewritten NTT / hash-tree code + unrolled keccak) | fastjs | fastjs |
| v3 | fastjs+native (both) | **keycache** (per-sk precomputation) | **pkcache** (per-pk precomputation) |
| v4 | bun runtime | bun runtime | bun runtime |
| v5 | 4 worker_threads (throughput) | 4 worker_threads | 4 worker_threads |

`v2`/`v3`(keygen) have no Falcon implementation, so those (variant, param) rows are skipped
(the contract allows skipping unsupported combinations); every other variant covers all 17 sets.

## Running

```bash
libs/noble/run.sh build
libs/noble/run.sh vectors results/noble/artifacts.json
libs/noble/run.sh crossverify results/noble/artifacts.json results/noble/crossverify-noble.json
libs/noble/run.sh bench --out results/noble/bench.jsonl                 # full run, 1 s budget
libs/noble/run.sh bench --out x.jsonl --budget-ms 200 --params ML-DSA-65 --ops sign --variants sign.v2,sign.v3
libs/noble/run.sh validate common/validation/validation.json.gz results/noble/validation.json
libs/noble/run.sh stages --out results/noble/stages.jsonl
libs/noble/run.sh memory --out results/noble/memory.jsonl
```

Timing follows the contract: warm-up ≥ 200 ms and ≥ 20 ops (capped at 3 s so multi-second ops run
once), then measure until the budget has elapsed and ≥ 3 ops (2 if one op takes > 5 s), cap 100 000
ops. Wall time is `process.hrtime.bigint()` per op; CPU is `process.cpuUsage()` (user+sys, all threads
of the process) over the measured loop. Every (variant, param) runs in its own child process so JIT
state, the hash layer and the runtime are isolated; the bun variants run `bun src/bench-one.mjs`.

Note on durations: noble's SLH-DSA "s" signing is slow in pure JS (≈2–8 s per op for SHA2-128s..256s,
≈7–21 s for SHAKE-128s..256s). The full bench therefore takes roughly 30–40 minutes, most of it in
`sign` on the six "s" sets.

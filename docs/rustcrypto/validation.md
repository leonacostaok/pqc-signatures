# rustcrypto: validation suite

`run.sh validate common/validation/validation.json.gz results/rustcrypto/validation.json`

## What runs

The suite (651 cases: NIST ACVP FIPS 204/205 keyGen / sigGen / sigVer vectors with contexts, plus the
negative/edge suite) is run through **every variant of the matching process**:

| case kind | variants | how |
|---|---|---|
| `keygen` | `keygen.v0..v5` | `SigningKey::from_seed(ξ)` / `slh_keygen_internal(SK.seed, SK.prf, PK.seed)`; pk **and** the FIPS-encoded sk compared with the expectation. `v5 par` generates 4 copies on the rayon pool and requires them to agree. |
| `siggen` | `sign.v0..v5` | the FIPS-encoded `sk_hex` is **imported** (`ExpandedSigningKey::from_expanded` / `SigningKey::try_from`), never regenerated; `sign_deterministic(msg, ctx)` / `try_sign_with_context(msg, ctx, None)`; `v4 keycache` decodes the key once and signs from the object; `v5 par` signs 4 copies. No SLH-DSA "s" cases are skipped (≈ 2–4 s each; the whole validate takes a few minutes). |
| `sigver` | `verify.v0..v5` + `total.v0` + `total_best.v0` | `verify_with_context` / `try_verify_with_context` (stateless), the cached-key closure (`v4`), 4 parallel copies (`v5`), and the two stage pipelines of section B. |

Each variant lives in one of the seven binaries (base / native / lto / mimalloc / pgo-keygen /
pgo-sign / pgo-verify), so `run.sh validate` runs all seven on the suite and merges the partial files
(`pqcbench validate-merge`) into the contract's `{results, summary}` JSON.

Malformed input handling: wrong lengths are rejected by the `TryFrom<&[u8]>` conversions before any
decoding; ML-DSA hint encoding rules (count ≤ ω, strictly increasing indices, zero padding) and the
`‖z‖∞` bound are enforced in `Signature::decode` (and re-implemented in the `decode.v1` fast unpacker
used by `total_best`); contexts longer than 255 bytes return an error. A panic would be caught by
`catch_unwind` and counted as `false` in the `panic=unwind` builds (base, native, mimalloc); the LTO
and PGO builds use `panic=abort`, so a panic there would abort the run — none occurred.

## Results

See the summary below (regenerated by the orchestrator) and `results/rustcrypto/validation.json`.
Dev runs on ML-DSA-44 and SLH-DSA-SHAKE-128f (all variants) and on the full suite were clean:
**no failures, no skips**. In particular every caching/precomputing variant (`sign.v4`, `verify.v4`,
and the `total_best` pipeline with its fast decoder and non-constant-time hint path) rejects the whole
negative suite (truncated/extended/zeroed signatures, flipped bits in R / FORS / HT / c~ / z / hint,
out-of-range z, hint count/order/padding violations, wrong contexts, wrong keys).

No library bug was found by the suite. Two observations worth recording:

* `ml-dsa` performs the `‖z‖∞ < γ1 − β` check inside `Signature::decode` (sigDecode) rather than in
  the verify body as FIPS 204 Alg. 8 writes it; the observable behaviour (reject) is the same and the
  stage split keeps the check in `hint_check` as well.
* `slh-dsa`'s `try_verify_with_context` carries a `// TODO - context processing` comment, but the
  implementation does prepend `0 ‖ |ctx| ‖ ctx` correctly — the ACVP context vectors pass.
